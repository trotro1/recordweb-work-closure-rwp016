## 1. Version-graph selection

Versions of one Assertion Record are grouped by verified `recordDid`. The verifier uses only verified `parents` edges to find the unique latest finalized head. Proof creation time does not establish succession. An incomplete graph, multiple finalized heads, or a missing head fails closed.

Resilience 03 creates a successor Version of the same `hasMandate` Assertion Record, changes its object to a replacement Mandate Record, and links the predecessor through `parents`. Only the successor is selected and the Case passes. This directly tests R-1.

Resilience 04 adds an attacker-signed pseudo-successor under the same Record DID. A Version can participate in the trusted version graph only when its verified signer matches the Record owner and that owner is authorized for the exact Case Version. The pseudo-successor is therefore ignored and cannot displace the authentic head.

Separate Assertion Record DIDs are not treated as revisions. Conflicting authorized assertions remain visible and fail closed. A withdrawal or a valid version-graph successor/merge is therefore needed for recovery; repeatedly publishing separate conflicting Records can keep validation blocked.

## 2. Predicate contracts

SHACL now checks:

- the declared object Record type for all eleven Work Closure predicates;
- exactly one selected `hasMandate`, `hasAuthorization`, `hasWorkAcceptance`, and `hasClosure`; and
- no duplicate selected `(subject, predicate, object)` assertions from separate Record DIDs.

Negative 31 replaces the required mandate assertion with a separately signed, authorized assertion whose object is an Authorization Decision Record. It is rejected by object-kind validation. Negative 32 adds a second authorized `hasMandate` assertion to the same object and is rejected by the singular/duplicate rules.

## 3. Proof and owner binding

The verified Case proof signer must equal the Case owner. For every Assertion Version, the verified owner-proof signer must equal both the Assertion Record owner and `assertedBy`, and that DID must be authorized for the exact Case Version. Negative 30 confirms that a Case proof signed by a non-owner fails closed.

The file `116_assertion_proof_verification_fixture_draft-0.9.json` is simulated proof-verifier output. It is not cryptographic evidence and does not make production proof-validation claims.

## 6. Limits

No real cryptographic proof is supplied. A production implementation must resolve each exact Version, validate ownership and proof signatures, verify the complete version graph, authenticate the Case-bound authorization policy, and retain verification evidence. Separate conflicting authorized Records may deny validation until an explicit correction/withdrawal mechanism resolves them. Passing these tests is not an RWP conformance, authority, evidence-truth, or legal-effect claim.
